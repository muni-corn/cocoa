# generating changelogs

i can automatically generate changelogs for you based on your commit history! they will be as
beautiful as i am~

## what is a changelog?

changelogs document changes in each release.

by default, i write Markdown. here's a sample from a small repository with two tagged releases
and one untagged fix:

```markdown
# Changelog

## **Next version**

### Bug fixes

- **ui:** prevent duplicate form submission

---

## **v1.2.0**

### **Breaking changes**

- **api:** redesign authentication endpoints

### Features

- **api:** redesign authentication endpoints
- **auth:** add password reset

### Bug fixes

- **core:** fix memory leak in parser

### Documentation

- update security docs

---

## **v1.1.0**

### Features

- **auth:** add two-factor authentication

### Bug fixes

- **utils:** fix timezone handling

---
```

a few things to notice:

- Versions are listed newest first, and each one ends with a `---` line.
- Commits that landed after the latest tag are grouped under **Next version**.
- A version's breaking changes are listed first. a breaking commit also stays in its own section
  (`api: redesign authentication endpoints` appears under both).
- Scopes are shown in bold in front of the subject.
- Sections are ordered by commit type: features, fixes, performance, tests, build, CI, docs, then
  everything else. entries inside a section are newest first.

voila! all generated by yours truly~

## generating a changelog

### write the changelog to a file

```bash
cocoa changelog
```

with no arguments, i read your whole history and split it into versions at your version tags, then
write the result to `CHANGELOG.md` (or whatever `output_file` is set to).

### preview without writing

```bash
cocoa --dry-run changelog
```

this prints the changelog instead of writing it. note that `--dry-run` goes before the command.

### generate for a specific range

```bash
cocoa changelog v1.2.0..HEAD
```

ranges use the `FROM..TO` form, with two dots. a range always produces a single section named **Next
version**, with no date, because i can't tell which release the range belongs to. this is handy for
release notes:

```bash
cocoa changelog --output release-notes.md v1.2.0..HEAD
```

### pick a different output file

```bash
cocoa changelog --output CHANGES.md
```

`--output` overrides `output_file` from your config for that run.

## output formats

choose a format with `--format`:

| Format             | Value                | Notes                                   |
| ------------------ | -------------------- | --------------------------------------- |
| Markdown (default) | `markdown` or `md`   | version dates are not shown             |
| JSON               | `json`               | the full changelog data, pretty-printed |
| HTML               | `html`               | a standalone page with escaped content  |
| reStructuredText   | `rst`                | headings show the version and its date  |
| AsciiDoc           | `asciidoc` or `adoc` | headings show the version and its date  |
| custom template    | `template:<path>`    | your own Jinja template, see below      |

```bash
cocoa changelog --format html --output changelog.html
cocoa changelog --format rst --output docs/changelog.rst
```

for example, reStructuredText looks like this:

```rst
changelog
=========

[v1.2.0] - 2024-03-14
---------------------

breaking changes
~~~~~~~~~~~~~~~~

* **api:** redesign authentication endpoints (``128c933e``)

features
~~~~~~~~

* **api:** redesign authentication endpoints (``128c933e``)
* **auth:** add password reset (``886fd726``)
```

the version date comes from the commit that the tag points at. HTML, reStructuredText and AsciiDoc
list the short commit id after each entry. markdown doesn't.

`cocoa release` and `cocoa tag` always use Markdown, whatever you pass to `cocoa changelog`.

### JSON

`--format json` writes the changelog data itself, so you can feed it to other tools:

```json
{
  "versions": [
    {
      "version": "v1.2.0",
      "date": "2024-03-14",
      "breaking_changes": [
        {
          "id": "128c933e",
          "commit_type": "feat",
          "scope": "api",
          "breaking": true,
          "subject": "redesign authentication endpoints",
          "body": null,
          "author": "demo",
          "timestamp": 1710439200,
          "date": "2024-03-14"
        }
      ],
      "sections": [
        {
          "commit_type": "feat",
          "title": "Features",
          "entries": []
        }
      ]
    }
  ]
}
```

`date` is `null` for unreleased versions, and `scope` is `null` when a commit has none. `body` is
currently always `null`, because only the first line of each commit message is read.
the `entries` list above is shortened. each entry has the same fields as a breaking change.

this is separate from the global `--json` flag, which wraps whatever was rendered (in any format) in
an envelope for scripts:

```bash
cocoa --json --dry-run changelog v1.2.0..HEAD
```

```json
{
  "content": "# Changelog\n\n## **Next version**\n\n### Bug fixes\n\n- ...",
  "format": "markdown",
  "path": "CHANGELOG.md",
  "dry_run": true
}
```

## configuration

customize changelog generation in `.cocoa.toml`:

```toml
[changelog]
output_file = "CHANGELOG.md"
include_merge_commits = false
date_format = "%Y-%m-%d"

[changelog.sections]
feat = "Features"
fix = "Bug fixes"
perf = "Performance"
docs = "Documentation"
refactor = "Refactoring"
breaking = "Breaking changes"
```

### key settings

| Setting                 | Default        | Meaning                                       |
| ----------------------- | -------------- | --------------------------------------------- |
| `output_file`           | `CHANGELOG.md` | Where to write the changelog                  |
| `include_merge_commits` | `false`        | Include merge commits                         |
| `include_reverts`       | see below      | Include revert commits                        |
| `date_format`           | `%Y-%m-%d`     | `strftime` format for version and entry dates |
| `sections`              | see below      | Section titles by commit type                 |

`include_reverts` is `true` when you have no `[changelog]` table at all, but a `[changelog]` table
that doesn't mention it turns it off. if you care either way, set it explicitly.

### section titles and which types appear

`[changelog.sections]` maps a commit type to the heading used for it. a commit type only appears in
the changelog if it has a title. these types have one built in, so they always appear:

| Type    | Default title          |
| ------- | ---------------------- |
| `feat`  | Features               |
| `fix`   | Bug fixes              |
| `perf`  | Performance            |
| `docs`  | Documentation          |
| `test`  | Tests                  |
| `build` | Build system           |
| `ci`    | Continuous integration |

types such as `refactor`, `chore` and `style` are left out unless you give them a title:

```toml
[changelog.sections]
refactor = "Refactoring"
chore = "Maintenance"
```

your titles take priority over the built-in ones, and the built-in types stay in even when your table
doesn't list them. there's no setting to hide one of them.

### custom section names

```toml
[changelog.sections]
feat = "✨ New features"
fix = "🐛 Bug fixes"
perf = "⚡ Performance"
docs = "📚 Documentation"
breaking = "💥 Breaking changes"
```

`breaking` is a special key. it's not really a commit type, but it sets the heading for the breaking changes
block at the top of each version. if you leave it out, it defaults to **"Breaking changes"**. Markdown,
HTML, reStructuredText and AsciiDoc all use it, and custom templates can read it too.

now i can make your changelog even nicer!

## custom templates

if none of the built-in formats suit you, write a [Jinja](https://jinja.palletsprojects.com/)
template and point me at it:

```bash
cocoa changelog --format template:tmpl/notes.md
```

here's a small template that lists breaking changes first and then each section:

```jinja
{% for version in changelog.versions -%}
## {{ version.version }}{% if version.date %} ({{ version.date }}){% endif %}

{% if version.breaking_changes -%}
### {{ config.sections.breaking|default("Breaking changes") }}

{% for entry in version.breaking_changes -%}
- {{ entry.subject }}
{% endfor %}
{% endif -%}
{% for section in version.sections -%}
### {{ section.title }}

{% for entry in section.entries -%}
- {% if entry.scope %}{{ entry.scope }}: {% endif %}{{ entry.subject }} (`{{ entry.id }}`)
{% endfor %}
{% endfor -%}
{% endfor %}
```

### variables

your template gets two variables:

- `changelog`: the same data as the JSON format. use `changelog.versions`, and for each version
  `version`, `date`, `breaking_changes` and `sections`. each section has `commit_type`, `title` and
  `entries`. each entry has `id`, `commit_type`, `scope`, `breaking`, `subject`, `body` (currently
  always `null`), `author`, `timestamp` and `date`.
- `config`: your `[changelog]` settings, for example `config.sections` and `config.date_format`.

a breaking entry appears in `breaking_changes` and also in its own section.

### things to know

- **whitespace is left alone.** a block tag on its own line leaves a blank line behind. use `-%}` or
  `{%-` to trim it, as in the example above. a trailing newline at the end of your template is kept.
- **escaping depends on the file name.** a template named `*.html`, `*.htm` or `*.xml` has its output
  escaped automatically, so `<` in a commit subject becomes `&lt;`. any other name is written as is.
- **the `heading` filter underlines text.** `{{ section.title|heading("~") }}` writes the title, a
  newline, and one `~` per character. this is handy for reStructuredText, where headings need an
  underline of the right length.
- **mistakes are reported.** a missing file, a syntax error or a failed render stops the command
  with a message that says which one it was.

## real-world examples

### example 1: simple feature release

commits since the last version:

```text
feat(auth): add password reset
feat(auth): add two-factor authentication
fix(auth): prevent concurrent logins
docs: update security docs
```

running `cocoa changelog v1.0.0..HEAD` gives:

```markdown
# Changelog

## **Next version**

### Features

- **auth:** add two-factor authentication
- **auth:** add password reset

### Bug fixes

- **auth:** prevent concurrent logins

### Documentation

- update security docs

---
```

### example 2: major release with breaking changes

commits:

```text
feat(api): add rate limiting
feat(api)!: drop v1 routes
```

the `!` after the type marks the second commit as breaking, so it's listed in a breaking changes
block at the top of its version, and again under its normal section:

```markdown
## **Next version**

### **Breaking changes**

- **api:** drop v1 routes

### Features

- **api:** drop v1 routes
- **api:** add rate limiting
```

### example 3: emergency hotfix release

just one fix:

```text
fix(security): patch authentication bypass vulnerability
```

generated changelog:

```markdown
# Changelog

## **Next version**

### Bug fixes

- **security:** patch authentication bypass vulnerability

---
```

## writing changelog-friendly commits

### good changelog commits

these look great in changelogs:

```text
feat(auth): add password reset
# clear, specific action :D

feat(dashboard): add user analytics
# specific feature :o

fix(ui): prevent duplicate form submission
# clear problem being fixed ^o^
```

### poor changelog commits

these don't read well:

```text
feat: stuff
# too vague :(

feat(auth): work in progress
# what kind of feature is that? >:T

feat(auth): add authentication
# okay? too generic though :c

feat(auth): add password reset and 2FA and OAuth and account linking
# consider breaking up your commits! </3
```

## how breaking changes are picked up

a commit counts as breaking in the changelog when its header has a `!` after the type or scope:

```text
feat(api)!: rename the rate-limit header
```

it's then listed under both the breaking changes heading and its normal section, such as
**Features**.

the changelog only reads the first line of each commit message. that means a `BREAKING CHANGE:`
footer is not picked up here, so use the `!` marker for anything that should show up as breaking.
for the same reason, commit bodies and footers such as `Closes #123` aren't printed, and `body` is
always `null` in the JSON format and in custom templates.

## releases

`cocoa release` writes the changelog as part of a release:

```bash
cocoa release
```

it does the same as running these yourself:

```bash
cocoa bump auto  # analyzes commits, bumps version (1.0.0 → 1.1.0)
cocoa changelog  # generates changelog
cocoa tag        # creates git tag with changelog
```

in order, `cocoa release`:

1. works out the next version from your commits.
2. updates your version files.
3. writes the changelog to `output_file`, always as Markdown.
4. commits the version files and the changelog.
5. creates an annotated tag whose message is the changelog.

it doesn't push anything. when you're happy, push the commit and tag yourself:

```bash
git push --all --tags
```

see [version management](./versioning.md) for details, including which version files are updated.

## tips and tricks

### 1. include more commit types

refactors, chores and style changes are left out by default. give them a title to include them:

```toml
[changelog.sections]
refactor = "Refactoring"
chore = "Maintenance"
```

### 2. release notes per version

to get notes for just one release, use a range between two tags. it's written as a single section
named **Next version**:

```bash
cocoa changelog --output releases/v1.2.0.md v1.1.0..v1.2.0
cocoa changelog --output releases/v1.1.0.md v1.0.0..v1.1.0
```

### 3. publish the changelog as a web page

```bash
cocoa changelog --format html --output public/changelog.html
```

### 4. highlight important changes

mark breaking commits with a `!`. i'll always put them first!

```text
feat(auth)!: redesign login flow
```

## troubleshooting

### "no commits found: changelog is empty"

this means i didn't find any commits to list. if you passed a range, check that it has commits in
it:

```bash
git log --oneline v1.2.0..HEAD
```

### "unknown output format"

the format must be one of `markdown`, `json`, `html`, `rst`, `asciidoc`, or `template:<path>`. check
the spelling, and remember that the template path goes right after `template:` with no space.

### "changelog looks empty or incomplete"

check that your configuration matches your commits:

```bash
# list recent commits with their types
git log --oneline | head -20
```

commits are only listed if they follow the conventional commit format and their type has a section
title. do your configured section names match your commit types?

```toml
# wrong
[changelog.sections]
features = "Features"  # not a commit type

# correct
[changelog.sections]
feat = "Features"      # match the commit type exactly
fix = "Bug fixes"
```

### "invalid range" or a git error about a revision

ranges use two dots, as in `v1.0.0..HEAD`. a value without dots gives `invalid range 'v1.0.0':
expected from..to`, and three dots (`v1.0.0...HEAD`) fail with a git error about the revision
`.HEAD`, because only the first `..` is treated as the separator.

### "changelog not updating"

here's a checklist:

1. did you run `cocoa changelog` without `--dry-run`? A dry run only prints the changelog.
2. is `output_file` set to the file you expect, and did you pass `--output` by mistake?
3. do your commits use types that have a section title?
4. did you create git tags for past versions? Without tags, everything is listed under **Next
   version**.
